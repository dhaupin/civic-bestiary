# Repository notes

**The Civic Bestiary** - a field guide to the characters of the body politic: satirical
portmanteaus for performative nationalism, bad-faith debate, hypocrisy, and algorithmic
radicalization. One dataset, three artifacts: a generated book (LEXICON.md), a hand-written
README that links to it, and a prerendered static site.

The frame is a naturalist's guide, and the vocabulary follows it everywhere: groups are
**chapters**, entries are addressed by their **kind** (species, move, ability, habitat, buff, fallacy),
the example is a **sighting in the wild**, and the cross-references are **compare with**.
Code follows too (`.species-*`, `.listing-*`), so a grep for "term" or "entry" should turn up
nothing but the prose in this file and the README.

The kind is not decoration: it decides which identification block a record must carry
(species: occasion / call / tell / counter; move: trigger / tell / counter; ability: effect /
available to / counter; habitat: carriers / economics / signature; buff: effect / tell /
expires; fallacy: family / committed when / the tell / counter; remedy: effect / costs /
failure mode / tell; keystone: office / call / tell / keystone) and which URL prefix the entry
lives under (`/species/`, `/moves/`, `/abilities/`, `/habitats/`, `/buffs/`, `/fallacies/`,
`/remedies/`, `/keystones/`). Changing a record's kind changes its URL, so a `_redirects` 301
has to follow it. The client's kind routes are derived from the schema, so adding a kind is a
data change and needs no edit to `AppLayout.jsx`.

## Layout

| Path | Role |
| --- | --- |
| `data/lexicon.json` | **Source of truth, meta half.** Title, description, preface, chapters. |
| `data/entries/<kind>/*.json` | **Source of truth, record half.** One file per term, filed under its kind's folder; the file name is the slug, and `kind` decides its URL. The folder must match `kind` - the loader fails loudly when it does not. |
| `schema/record.json` | **The record contract.** Fields, kinds, identification blocks, and the relation vocabulary. `build.py`, `build_schema.py`, and the site all derive from it. A kind may `omit` a field: fallacies have no pronunciation. |
| `packs/public/bestiary-shapes/` | The site's own verifier pack (packstruct SPEC v1): asserts the identification block, the field-guide links, and the read-more rows survive to baked HTML. |
| `poststruct.config.mjs` | Arms the artifact audit: points it at `web/dist`, arms the pack, names `data/` as the prose of record. |
| `README.md` | **Authored.** The project's front door: what it is, how it is built, how to run it. Its one generated block sits between `<!-- BEGIN:generated -->` and `<!-- END:generated -->` - edit around it, never inside it. |
| `LEXICON.md` | Generated by `build.py`: the whole guide as one markdown document. Never hand-edit. |
| `site.config.js` | **Identity**: name, wordmark, URL, nav, base routes, 404 copy. Adopted from `dhaupin/coreforge`. |
| `web/` | The site: coreforge's React/Vite shell, prerendered by `dhaupin/prestruct`. |
| `web/src/data/lexicon.js` | Generated by `build_site.py`; the app's only data import. |
| `web/src/data/contract.js` | Generated by `build_schema.py`; what the contribute page renders. |
| `web/ssr.config.js` | Adapter: reshapes `site.config.js` + entries into prestruct config, including one route per entry at its kind's prefix and the `DefinedTermSet` JSON-LD. |
| `build.py` / `build_site.py` / `build_schema.py` | Generators, stdlib only. All three take `--check`. |

## Commands

```bash
python3 build.py            # regenerate LEXICON.md + the README block
python3 build.py --chapters # audit: fallacies filed against the commit graph
python3 build_site.py       # regenerate web/src/data/lexicon.js
python3 build_schema.py     # regenerate the issue form + web/src/data/contract.js
npm run check               # CI gate: all three --check runs, plus pack lint

npm run audit               # poststruct over web/dist: head/site/links/i18n/a11y/language + our pack
npm run lint:packs          # packstruct lint over packs/ --deep
npm run verify              # check + build + audit, end to end

npm --prefix web install    # once
npm --prefix web run build  # prestruct: validate -> vite build -> inject meta -> prerender -> audit
npm --prefix web run dev    # local dev server
```

`npm run build` at the root runs all three in order.

## Branches

`staging` is the integration branch; `main` is what publishes.

1. Work lands on a topic branch and PRs into `staging`. The `site` workflow runs
   the full gate there (artifacts current, pack lint, build, poststruct audit) -
   the same gate as main, minus the deploy.
2. Promote with a PR `staging` -> `main`. Only `main` publishes: the deploy job
   is gated on `github.ref`, so a green staging run is the evidence a promotion
   carries, not a deploy.
3. On every push to `main`, `staging-ff-sync` fast-forwards `staging` onto main,
   keeping it a mirror rather than a second line of history. It also restores
   `staging` if a promotion PR was merged with `--delete-branch`.

Never commit to `main` directly, and never force-push `staging`: a divergence is
meant to fail the sync job loudly, because that means a commit landed on staging
that main does not have.

Promote with a merge commit (`gh pr merge --merge`), not a squash. A squash lands
the content on `main` without staging's commits, so staging stops being an ancestor
of `main` and `staging-ff-sync` fails - by design, since it cannot tell that
divergence from a real one. Recovering means deleting `staging` and re-running the
sync job, which recreates it at `main`.

## Validation

`build.py` refuses to render when a term is duplicated, an entry is missing a required field,
a `related` reference is undefined or self-referential, a section id is unknown, or a term is
never listed in anyone else's `related` list (the cross-reference graph must stay connected).
After rendering it also verifies every internal `](#anchor)` target resolves.

`build.py` also refuses a record whose file name does not match its term's slug, a missing or
duplicated `order` inside an order, and an order with no species.

`prestruct build` fails on config errors and grades the baked HTML; a red audit is a real
defect (missing or duplicate title, bad canonical, absent OG tags, over-long description).

`poststruct` then audits the artifact prestruct just baked - the cheap half we do not write
ourselves: the internal link graph, i18n tags, a11y-lite (informative images, labels, skip
link), the site/feeds contract, and the language module (dash classes FAIL by default, so the
` - ` house rule is enforced rather than remembered). It also runs `packs/`. CI pins both
(`poststruct@1.2.0`, `packstruct@1.1.2`): an audit that floats is not a gate.

One build warning is expected and harmless: `[IMPORT_IS_UNDEFINED] Import 'default' will always
be undefined` at `src/hooks/usePageMeta.js`, from the deliberate v6/v7 interop shim in that file.
It does not fail the build; do not "fix" it by deleting the fallback.

## Adding an entry

1. Add `data/entries/<kind>/<slug>.json`, in the folder for the kind you are writing. `slug` is the term lowercased with spaces as hyphens, so
   `Trust-Me-Brofessor` is `trust-me-brofessor.json` - the validator refuses a mismatch. Set
   `kind`, `chapter`, and `position`. Coinages number from 1 and the fallacies in the same chapter
   start at 101, so the coinages always sort ahead of the documented errors; append within your own
   block, one past its highest, because inserting mid-chapter shifts every book anchor below it.
   The 101 is a spacer, not a rule about density: the invariant is that every coined entry sorts
   ahead of every reference entry in its chapter, and the validator enforces it. `position` sets
   that order only - the book numbers entries by running count, so "No. 7 of 187" is the entry's
   place in the guide, not its position. Fill the identification block the kind requires, and no
   other kind's block.
2. Add the new term to one existing entry's `related` list, swapping out its weakest link -
   lists are kept at three items, and the validator tells you if you skipped this.
3. `python3 build.py && python3 build_site.py`, then `npm --prefix web run build`.
4. Review the LEXICON.md diff, the README counts block, and the new entry page.

## The eight kinds, and what each one is for

The taxonomy is the joke's grammar, so a record's kind is an argument about what the thing is:
a **species** is a pattern of behaviour you can name, a **move** is something done in front of
witnesses, an **ability** belongs to an office rather than a person, a **habitat** is where the
performance is fed, a **buff** is a temporary condition, a **fallacy** is a real error with a
citation, a **remedy** is a procedure that answers one, and a **keystone** is the office whose
absence is the pathology.

The last two are the answer side of the guide, and the reason it is not a list of complaints: a
remedy is something a person or a body can do (notice and comment, the carve-out, the stay), and
a keystone is an institution that has to exist before the answer is available at all (the clerk,
the auditor, the poll worker, the redistricting commission). When a proposed entry is hard to
place, ask who holds it - a body, a room, a clock, or a person - and the kind usually falls out.
If the honest answer is "nobody, and that is the problem", it is a keystone.

## Sort axes

`schema/record.json` owns `sorts`: three axes every record scores 1-5, and a `sorts` list per kind naming
which apply. Today all kinds carry all three.

| axis | question it answers |
|---|---|
| `impact` | how much damage it does to the thing it touches |
| `abuse` | how often you actually meet it |
| `blowback` | what it costs the one who uses it |

`sort` is a field on every record and `build.py` refuses an entry that skips an axis its kind supports or
scores outside 1-5. The site reads them through `sortByAxis()` in `src/lexicon.js`; views default to `impact`,
except `/fallacies/`, which opens on `abuse` - the most abused first, which is the order that page is for.

Sorting is **within** a group, never across one: a chapter keeps its chapters, a family keeps its family, and
the coinage/fallacy seam keeps its seam. Ties fall back to `position`, so the order is identical in the
prerender and after hydration. `position` is the curated field order and stays available as "Field order".

## The fallacies

The documented fallacies live in `data/entries/` beside the coinages, as `kind: fallacy`. They are not
coinages: the review bar is that the account is real and traceable, so every fallacy record carries
`cite: { label, url }` pointing at its Wikipedia article (verified to resolve - do not add one without
checking). Definitions are written in the guide's voice; nothing about the mechanism may be invented. Those
pages have no `ipa`.

## The sources

A coinage is invented. The thing it is built on usually is not, and that is what a reader who suspects the
guide of making things up will go looking for. So a coinage cites its **referent**: the pocket veto, the
shadow docket, the blue slip, the ombudsman, the poll worker. `cite: { label, url }`, label first naming the
source (`Wikipedia · Shadow docket`), URL verified to resolve. A character with no real referent - the
passoffist, the sabottriot, the honeymoan - carries no `cite` and says so by leaving it empty.

Two rules, both enforced by nothing but attention:

- **Cite the thing, not the word.** The citation points at the doctrine, office or procedure the character
  names, never at a page that would only exist because this guide exists. Do not cite the coinage back to
  itself.
- **Verify, then write.** `curl -sIL <url>` before the record lands. A dead link is worse than no link: it
  tells the sceptical reader they were right.

**The graph is the default, not the law.** A fallacy belongs to the chapter whose characters commit it - count
the `commits` edges into it and take the majority. If the committers split across chapters, no chapter owns it
and it goes to chapter `normalization` ("Normalization, Numbness & the Noise Floor"), which is where tu quoque,
whataboutism and cherry picking live, because every chapter uses them.

While the book is being built the author may file against that default: a fallacy can sit where it reads best,
or where a chapter needs it, and the count can be argued with later. What must not happen is the disagreement
going unnoticed, so `python3 build.py --chapters` prints every fallacy whose `chapter` the graph does not point
at, with the tally behind it. A clean report means the filing and the edges agree; a dirty one is a decision
someone made on purpose and should be able to defend. The better fix is still to move the `commits` edges -
re-file a fallacy by changing which character commits it - because a chapter that is right about a fallacy and
has no character to commit it is a chapter that has not been written yet.

That chapter is not a leftovers bucket, and the name says why: a fallacy every chapter commits is one the room
has stopped noticing, so "no character owns it" *is* the thesis. Its own species are the ones who keep the room
as it is - the passoffist manages the temperature, the provocrop wears the slogan - and they commit the ambient
fallacies rather than owning them, which is the point rather than a filing coincidence.

Within a chapter the coinages come first and the fallacies follow behind a "Documented fallacies" sub-head, so
each chapter reads as the joke and then its receipt.

They are in the same dataset on purpose: one search, one sitemap, one book, one browse surface. Their own
index is `/fallacies/`, and the kind chip plus the chapter chip reach them from the guide.

Inside the appendix the listing groups by **family** (Red herring, Presumption, Ambiguity, Faulty
generalization, Questionable cause, Statistical, Improper premise, Relevance) rather than by chapter, because
every fallacy is in the same chapter and a chapter heading there says nothing. `pages/Guide.jsx` switches the
grouping when the view is `/fallacies/` — same component, different axis.

The list is ordered by how often each one is actually used: the standard canon first, then the ones that live
in comment sections (tu quoque, whataboutism, sealioning, gish gallop, nut-picking, "I'm entitled to my
opinion"). Adding the next tier is a record, a verification of its source URL, and at least one `commits`
edge — the validator rejects an unreferenced term.

## Habitats house fallacies too

`houses` runs habitat → species, move, **and fallacy**, so a place can be the answer to "where is this
abused". Comment section, Cable panel, and Group chat are habitats whose `Houses` lists are all fallacies,
and each fallacy page derives "Found in" from the same authored edge. That is the whole reason the relation
is a vocabulary: extending it to a new pair of kinds is a schema edit, not a new renderer.

A relation that points at more than one kind is split by kind wherever it renders - in the book and
on the entry page - because a flat list of links cannot say which is a person, which is an action and
which is a documented error. `houses` says "Species you'll meet here", "Moves you'll see here" and
"Fallacies at home here"; every other mixed list falls back to the kind's plural ("Species",
"Habitats"). The split is derived from each link's `kind`, which `build_site.py` stamps onto every
edge and backlink, so a new pair of kinds needs no renderer change. One kind and the list stays flat.

## Linking two entries

`edges` is a controlled vocabulary, not prose: `{ "rel": "houses", "to": "Patriotainer" }`.
The relation decides which kinds may point at which (a habitat houses a species; a species
performs a move; anything in the guide commits a fallacy), so a wrong-direction edge is a
validation error rather than a silently one-way link. Author one direction only -
`build_site.py` derives the inverse ("Found in", "Committed by"), so the target page shows it
without anyone writing that sentence, and authoring both sides is an error. `related` stays
the untyped fallback for a connection the vocabulary cannot name.

The graph must stay connected, but `related` is no longer the only way to connect: a term is
reachable if it appears in a `related` list **or** is the target of any edge.

A fallacy is filed by the argument it names; the characters that commit it are filed by what
they do. So a fallacy page also derives "In chapters" from the chapters of the entries whose
`commits` edge points at it. The line appears only when it says something the breadcrumb does
not - two or more chapters, or one chapter that is not the entry's own - and it moves nothing:
the authored `chapter` stays where it was.

The site slug is derived from the term (`Trust-Me-Brofessor` becomes
`/species/trust-me-brofessor`), so it is stable; the prefix is the kind's. `LEXICON.md` anchors are
GitHub's auto-generated heading anchors (`#10-trust-me-brofessor`) and therefore **do** shift
when an entry is inserted mid-chapter. That is the one thing a renumber breaks; prefer
appending.

## Site notes

- **The taxonomy owns the path; the refinements own the query string.** `/guide/` is
  everything, `/chapters/<id>/` is one chapter, and each kind's prefix (`/species/`,
  `/moves/`, `/abilities/`, `/habitats/`, `/buffs/`, `/fallacies/`) is that kind's front door -
  all prerendered pages with their own title, built from one component (`pages/Guide.jsx`).
  What narrows the view without being the page - search (`?q=`), a letter (`?letter=`), a sort
  (`?sort=`) - lives in the query string, so a filtered view is still a link someone can send,
  and the vocabulary is one `PARAM` map in that file.
- **Kind and chapter combine.** The one the reader clicked last owns the path and the other
  rides along as `?kind=` or `?chapter=`, so `/chapters/ii/?kind=species` is the species in
  chapter II rather than a lost filter. Every chip and tag link rebuilds the URL through one
  `linkFor` helper, which is what keeps the other filters alive. Canonicals stay on the path,
  so the parameter variants are not separate pages and never reach `sitemap.xml`.
- **Numbers are counted, never typed.** The README block, the book's footer, the home stats,
  and the `/about/` and `/contribute/` counts all come from `data/` - `build.py` writes the
  README block and the book, `build_site.py` writes the bundle the site reads. Which kinds count as coinages is
  `coined` on the kind in `schema/record.json`, not a list in the build script. If a document
  needs a figure, point at the block instead of copying it; `labs/prd-codex.md` does.
- **`/fallacies/` is the appendix index**, and `/fallacies/<slug>/` its entries - the same
  component as every other kind, so the drill-downs, the A-Z filter, and the search all work
  there without a second implementation.
- **`/guide/` was `/species/`.** The guide used to live at `/species/`; that path is now the
  species front door, so there is no redirect to write (a path cannot both serve and redirect).
  Inbound links land on the 24 species with a link to the whole guide.
- Entries that changed kind since launch 301 from their old `/species/` URL in
  `web/public/_redirects`.
- **Route paths, links, and canonicals all carry a trailing slash.** Cloudflare Pages serves
  a prerendered directory route at `/species/playtriot/` and 308-redirects the slashless form
  (verified against the family's own Pages sites). Declaring routes as `/species/<slug>/` keeps
  the canonical equal to the served URL and saves a redirect on every click. If you add a
  `Link` or a route, match that form.
- **Adopted from coreforge, deliberately trimmed.** The shell's Jekyll `docs/` rig and its
  paint-scheme preset picker are not shipped: this site has one palette and no docs site.
  Everything else follows the family rules - tokens own the palette, theme is one
  `<html data-theme>` attribute, nav and footer render from `site.config.js`.
- **`siteUrl` is the canonical origin** (`https://codex.creadev.org`), attached to the Pages
  project as a custom domain. It is baked into canonicals, OG tags, JSON-LD, `sitemap.xml`, and
  `llms.txt`. Changing it means changing that one line in `site.config.js` and rebuilding - not
  editing the baked files. `civicbestiary.pages.dev` still serves the same build, so it needs a
  zone-level redirect if the duplicate host should not be indexed.
- The repo URL is authored once, in `site.config.js` (`REPO`); the nav link, the footer, and
  the JSON-LD license all derive from it. A few surfaces still carry hand-copied identity and
  will drift on a rename: `web/public/site.webmanifest`, the `aria-label` in
  `web/public/icon.svg`, the canonical placeholder in `web/index.html`, the two
  `package.json` names, and the OG `alt` in `web/ssr.config.js`. Check them on any rename.
- `web/public/icon.svg` is the authored mark; `npm --prefix web run icons` re-rasterizes the
  favicons from it. `@resvg/resvg-js` is a dev dependency for that and for the social card, so
  there is nothing to install by hand.
- `web/public/og-image.svg` is **generated** by `web/scripts/og.mjs` from the counts in
  `lexicon.js` and the identity in `site.config.js`, and `og-image.png` is rasterized from it on
  every build (`npm run og` runs first in `web`'s build). The card is content, not identity: a
  card claiming a count the guide no longer has is a claim the guide disproves. The SVG is
  committed because it is text and `--check` can compare it exactly; the PNG is not, because
  rasterizer output is not byte-stable across platforms. Edit the data or `site.config.js` and
  rebuild - never the SVG.
- `web/public/og/<kind>/<slug>.png` is **generated**, one card per entry, by the same script in
  the same pass: a shared Bootcurious shows Bootcurious, not the site card. Nothing about them is
  committed - they are derived from the records, which are the reviewed artifact - and the
  directory is wiped and rebuilt each run so a renamed entry cannot leave a card behind at a URL
  nothing links to. The URL carries `?v=<hash of what the card prints>`, computed in
  `build_site.py` and emitted as `entry.og`; `web/ssr.config.js` puts it in the route's
  `ogImage`, and `usePageMeta` keeps it in step on client-side navigation. A changed entry is
  therefore a changed URL, and scrapers refetch instead of serving the old card.
- **Deploy is Cloudflare Pages, built from Git.** The dashboard must hold exactly:

  | Setting | Value |
  | --- | --- |
  | Production branch | `main` (other branches get preview deployments) |
  | Root directory | `web` - case-sensitive; `Web` fails with `Cannot find cwd` |
  | Build command | `npm run build` |
  | Build output | `dist` - relative to the root directory, so **not** `web/dist` |

  Both failure modes are silent-ish: a wrong case dies before the build starts, and a wrong
  output path builds fine and deploys an empty site. `web/.nvmrc` pins Node - Pages and CI
  read the same file.
- There is no deploy job in CI: `.github/workflows/verify.yml` only gates (artifacts current,
  pack lint, build, poststruct). A second build in CI could only disagree with the one that
  ships.
- `web/public/_headers` and `web/public/_redirects` are Cloudflare's control files; they are
  copied into `dist/` as-is. The SPA fallback (`/* /index.html 200`) must stay out of
  `_redirects` - with prerendering it loops against CF's Pretty URLs.
- `web/functions/api/health.js` is the Functions canary (`/api/health`). If it 404s, the
  root-directory setting is wrong, not the function.
- `.prestruct/cache/` makes rebuilds incremental; `npx prestruct clean` clears it.
- **The header carries reading surfaces; the footer carries the paperwork.** `nav` in
  `site.config.js` holds Field guide / Fallacies / About (all `group: 'site'`), and
  `footerExtras` holds Contribute / GitHub / License. The header, the burger sidebar, and the
  footer all render from those two lists - do not hand-type a nav link in a component.
- **`/about/` is the essay.** The landing (`pages/Home.jsx`) is browse-first: hero, a random
  entry, the chapter map, the answers. The preface prose lives on `/about/`, which reads it
  from `lexicon.json` so it cannot drift from the book. Adding a landing section is cheap -
  it should send a reader into an entry, not into an argument.
- **`labs/*.md` is served from the site.** `build_site.py` copies it to `web/public/labs/`, so
  `labs/prd-codex.md` (the product + record contract) resolves at `/labs/prd-codex.md`, which is
  what the contribute page's "Read the record contract" button points at. Edit the file in
  `labs/`; the copy is generated.
- **The issue form needs its label to exist.** `.github/ISSUE_TEMPLATE/new-entry.yml` declares
  `labels: ["new-term"]`; if that label is missing from the repo, GitHub silently renders a
  blank issue instead of the form. Check the label before debugging the template or the URL.

## House style

- Two numbered senses per entry: one concrete ("who this person is"), one structural ("what
  the pattern does"). `notes` is optional and only for etymology or usage caveats.
- The cast is characters, not animals. A species is a **character**; anything in the book,
  whatever its kind, is an **entry**; a move is what a character **does**. "Creature" and
  "animal" are retired - the field-guide frame stays (bestiary, habitat, tell), the fauna does
  not.
- Every entry carries exactly the identification rows its kind declares in
  `schema/record.json` (`kinds.<kind>.identification`), and `build.py` fails without them:
  `species` takes occasion / call / tell / counter, `move` trigger / tell / counter, `ability`
  effect / available to / counter, `habitat` carriers / economics / signature / counter, `buff`
  effect / tell / expires, `fallacy` family / committed when / tell / counter, `remedy` effect /
  costs / failure / tell, and `keystone` office / call / tell / keystone.
  They render as the identification block on the entry page and in the book, between the
  etymology and the senses. The `tell` values are what a reader scans before reading the prose,
  so they stay concrete and observable.
- `confused_with` is the pair edge: `[{ "term": "<existing term>", "tell": "<how to tell them
  apart>" }]`. The `tell` is the whole point - it must be a diagnostic ("the sophistroll knows
  the fallacy is a fallacy; the illogician believes it"), not a restatement of either entry.
  A twin is filtered out of `related` by both generators, so the same species never appears
  under both "Easily confused with" and "Compare with".
- Counters are authored from the side that ends it: the remedy or keystone carries the
  `counters` edge, and the coinage's page renders the inverse. A coinage whose `counter` prose
  names a procedure the guide already has should point at it - the prose and the graph saying
  the same thing in different places is how a page ends up describing an answer it does not
  link to. Buffs are the exception: their identification row is `expires`, not `counter`, so a
  buff with no `counters` edge is not a gap. If one is later needed, wire it then.
- `part_of_speech` and `ipa` use the loose conventions already in the file; IPA is
  approximate and follows the coining, not a dictionary.
- Prose uses ` - ` (spaced hyphen), never an em dash. Quotes are straight everywhere - data,
  book and site - and nothing converts them at render time. Curly quotes break copy-paste, and
  the entries are written to be quoted from; the validator and the diff both stay honest when
  one character means one character.
- The example is one line of reported speech, with the coined term in `**bold**` and the
  whole quote in italics. It is the "sighting in the wild"; `call` is the different thing -
  what the character says, not what someone says about it. Reference entries are the
  exception: a fallacy quotes the sentence that commits it, then says what it does, and has
  no coinage to bold.
- `related` never repeats a `confused_with` twin. Both generators filter the twin out of the
  compare list, so the link would render nowhere; it is dead data, not a second connection.
- Voice is satirical and pointed, aimed at behavior, institutions, and power - never at
  identity, and never at the people on the receiving end. The bestiary frame carries the
  rule: the species is the pattern, not the person.
- Some species are trolls in the old sense (things under bridges demanding a toll), some in
  the internet sense. The preface says so; keep new entries consistent with whichever
  lineage they belong to.
